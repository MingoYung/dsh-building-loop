# 受控项目结构

上级为[项目文件与接手](../docs/project-files.md)。三个层级分别保存项目总纲、分块索引和实际正文。新建的会话私有项目自动保护 `PROJECT-GOAL.md` 中的「分块入口」及 `INDEX.md` 中的「模块正文」。已有授权工作区可在清单里登记自己的文件、章节和正文路径。

```json
{
  "hierarchy": {
    "overview": {"path": "PROJECT-GOAL.md", "heading": "分块入口"},
    "index": {"path": "INDEX.md", "heading": "模块正文"},
    "modules": {"restore-policy": "modules/restore-policy.md"}
  }
}
```

显式授权模块时用精确路径。宿主自动建档的会话私有项目使用 `modules/<模块标识>.md`。例如所有者在当前会话发出 `新增模块 restore-policy：恢复策略`，总控可以调用 `building_loop_file` 的 `add-module`，携带 `module`、`title`、实际 Markdown `content` 和 `note`。宿主校验真实用户消息与参数一致，检查导航锚点唯一，并把二级入口和正文链接放到已有对应章节。随后按总纲 → 分块索引 → 正文核对真实可读的路径。无关段落与既有正文保留原字节。

普通受控写入可指定 `heading`，在原位更新一个已有章节的内容。追加同名章节、改章节结构、改保护的导航区或拆开写入已登记的新模块时，工具会指出阻塞原因。一次新增模块通过现有文件历史和事务机制发布，提交前对照实际导航及正文的字节。遇到外部编辑器修改受影响文件时，保留能识别的旧版本及外部修改，由宿主恢复或提示核对。新正文没有改前版本，实际改动的导航文件继续使用各自的单份滚动备份。

现有工作区按原权限运行，登记 `hierarchy` 后启用检查。为老项目接入时，总纲须在 `goalContext`，总控要能读两级导航，并读写登记的精确正文路径。新增模块发布的是一份文档和导航，总控可沿路径读回，现有子会话授权和工作单元继续按清单管理。部署前可用一个新模块演练：验证重复标题与越权写入被拦，成功后实际打开三级文件，核对其他章节的字节及日志。

## 架构验收和原地接手

签名代码工作单元可登记 `architecture: {"module":"architecture","headings":["模块职责","实施顺序","回退顺序","关键验证"]}`。`module` 必须是 `hierarchy.modules` 里已有的模块编号。总控有精确写权限，两个核验角色有读权限，执行方沿原授权仅编辑代码。总控先写正文，再用 `building_loop architecture` 登记。宿主确认两级导航和每个标题的实质正文。实际职责、依赖、回退与验证是否正确，由两位核验者按当前源码和测试各自判断。架构变更重新登记，旧版本的核验不用于新稿关单。

同目录接手工程时，在新会话的开工消息单独写明 `工作单元 K02。`。宿主将该单元与当前目标文件、授权版本及前一次总控绑定。前序关单后可以转交总控权限，旧回执、来源与账目原始身份仍可核对。旧单元因目标改变已经阻塞时，用户可以另外单列 `以新目标替换工作单元 K01。`，由宿主记录旧单元未完成而被替换。仍处于可写阶段的旧单元须先退出该阶段。新会话从当前文件、已验收记录及未结账目接手。

若前一次会话已进入工程规划并写了架构稿，但从未派单，所有者可直接在同目录的新会话确认不同目标及新单元。宿主验证旧规划会话、实际目标变化和账本记录，保留原架构稿，转移后旧会话失去写权限。

## 可执行架构示例

签名工程可在维护者策略的 `architecture.examplesHeading` 登记一个实际要求的架构章节。该章节正文仅有一个 JSON 围栏，其中包含 1–8 个独立示例。每条给出唯一 `id`、授权 `recipe`、可选 `stdin`、`expectedExitCode` 和可选 `expectedJson`。运行配方必须在对应单元的 `codeTask.diagnostics.reviewRecipes` 登记，编译配方单独保留。

总控在派单前登记示例输入与预期。首审和独立复核分别用 `building_loop_code_review probe` 的 `assertion: "architecture"` 一次运行全部示例，也可提供 `exampleId` 单独复查。必跑示例不占用探索复现的配额。当前签名版本必须和全部示例结果一致才可批准。实际差异定位到架构稿与对应示例，退回总控更新。源码若不符合要求，另按其实际责任退回执行方。两位审核者仍须对照真实源码检查架构其余文字和必要注释。

启用 Python 静态导入章节的项目还会在签名后对照能明确定位的现行直接调用、导入和模块职责。模块名开头的明确陈述如果把函数实现归给实际调用它的模块，或者把某字段的校验与错误码归给实际只调用该校验函数的模块，宿主报告架构稿行、真实模块、函数及源码行，交总控修正后再进入原核验阶段。职责归属需要有可定位的唯一实现和确定的调用关系。别名不确定、动态加载、职责共享或委托关系仍由两位核验者根据实际源码判断。

明确标注「导入方向」或「静态导入关系」的完整箭头表达式允许唯一模块别名、括号分组和末端斜杠列表。宿主核对每条直接导入。工作流图、未知别名和省略中间节点的叙述仍由审核者解释。明确列举的字段校验、字面错误码的拒绝分支、以及把原始 JSON 交给某模块解码的描述，可由对应的唯一源码位置补充核对。宿主要求定位到实际字段守卫、拒绝语句或可解析的 `json.load` / `json.loads` 调用。没有唯一证据、存在同模块实现或调用绑定不明确时仍进入独立审核。

架构登记或返修前，获授权的总控可用 `building_loop prepare` 查看登记源码是否存在。完整解析时同时显示当前本地直接导入的文件名。未能读取的文件标为未知。宿主校验正文中明确声称当前缺失的登记源码，并在签名后校验明确的现行导入和职责归属。总控可以据此准确说明现状及拟改方向，源码正文仍由原执行、核验角色按授权读取。
