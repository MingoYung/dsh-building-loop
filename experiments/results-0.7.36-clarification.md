# 0.7.36 · 审核参数与用户澄清

上级为[实验与验收](README.md)。前一轮原生记录见 [R80](observations-0.7.35-delivery-outcomes.json)。

## 真实审核反复补参的根因

| 现象 | 原始调用与成功回执 | 处理 |
|---|---|---|
| 独立复核同一项目规则块反复报缺规则或前提 | 失败包已有规则和前提，但写在 `parts[]` 顶层；部分包只移动了 `rule`。真实 `prepare` 示例也把 `rule` 展示在顶层。规则、证据和判断移到同一个 `inference` 后获得回执 | `prepare` 提供嵌套示例，报告实际放错的字段。纯规则允许空前提，需要应用到记录时仍须交已核原始材料 |
| 首审和独立复核反复重交相同处置 | 成功与失败的处置值及定位不变。本角色对具体位置的覆盖证明改成新版类型后才过。原错误只报第一个事项和「正文或大白话」 | `coverage status` 和最终拒收列出本角色全部未满足的证明、事项、正文或大白话的实际行及覆盖块，已正确的处置回执可原样提交 |
| 独立复核第一次已有正文和大白话的位置，仍报位置不足 | 真实输入缺的是同级 `decision` 字段 | 分开报缺处置值与缺位置。准备包标清独立复核何时需要自己的 `outcomes` |

遗漏标点、使用未登记的原文行和未填 `sourceRelation` 仍按真实证据或实际入参处理。两道审核仍分别判断证据能支持的内容，最终审核和关单继续用角色各自的当前证据。

已批准的原生用例使用一条演练发布记录和一份带采集摘要的 GitHub 官方摘录。记录同时给出失败的自动检查和放行的人工复核；当前项目规则没有指定两者谁优先。等待状态必须来自原生宿主，不使用任何预置的用户回答。Windows 确定性覆盖分别演练两条业务决定，并维持当前实际原文校验。

首段的审核者曾将「待确认」放到 `decided`，后来选择 `missing`，使原执行会话返工两次。一次返工在没有项目口径时擅自写成拦下，被重新审核拒绝。真正的澄清尝试里，问号后的续做说明还触发了旧的「问题须结束于问号」校验。小范围处理将明确处置、缺少处置和待用户决策的参数分开报错，一个具体问题有后附操作说明时只转发问题，多个问号仍须明确要问哪一个。旧稿、无效结果和跨角色证明的门槛继续回归。

真实会话在 252.628 秒由宿主落盘 `blocked`。试验观察器起初要求问题出现「检查／失败／退回」，把使用「两类意见／拦下」的有效问法拒绝了。恢复观察器时，仍使用同一 Windows 隔离 Profile 和原总控、执行方、首审，校验了 25 个检查点文件，保留原总纲和候选稿的摘要。原生重连后没有新模型调用，收到真实用户回答前保持原业务决定未定。修正问题格式的候选包另行校验 58 个文件及两种选择的宿主流程，全量回归 474/474。正在等待的同一真实会话继续用已经验证的原候选字节。

用户回复「你决定」，委托本轮处理。转发给原 DSH 会话的消息保留这段原话，另明确代理决定「以自动检查失败为准，退回重跑」。第一次恢复接收消息并自动记账，总控随后两次误用 `edit PROJECT.md`，三次在总纲未更新时推进均被宿主拦截。注册工具将 `write` 描述为新建文件用，与已有总纲其实支持的 `write` 路径冲突。

修复后的宿主在 `prepare` 和 `status` 给出当前被授权总控可用的文件读取、按原有章节写入、带原单元编号推进三步。没有总纲写权限时明确由维护者修改。总纲换版后只给原单元推进提示，不再展示旧问题。测试通过真实工具验证正确章节和滚动备份；错误章节仍被拦截。

恢复实跑继续用原包以避免换掉待验证会话。只发送一次技术操作提示，原用户决定没有重复发送，测试器也没有代写总纲。原总控实际只修改总纲第 6 行，滚动备份与原总纲字节一致。原首审先退回仍写「待确认」的旧稿，原执行方随后在正文及大白话都写入明确结果「退回重跑」，保留两份来源和原始记录。

更新总纲工具说明的候选通过专项 18/18、Windows 全量 475/475 和隔离 Windows DSH 的 58 文件核对，两种人工决定在安装后零模型对照都走到关单。原真机会话使用原包、经技术提示恢复，总控和原子会话写稿审核成功后进入独立复核，五处分歧经一轮重核剩一处，真实运行为 `blocked`，两条自动账目仍待处理。

冻结的末次两份实际证明对同一摘要和处置引用了相同原始记录及同一条完整业务规则。一方额外引用了总纲中要求逐项交付并在末尾用大白话复述的条款，旧的规则引用集等价检查因此错误判定分歧。修复只在两份独立正文和摘要已经分别绑定确切处置、完整业务条款和同一原始记录时消去纯格式引用造成的差异。额外例外、缺少业务条件、更换前提、正文分歧或摘要加入实质断言继续触发重核。新版加载到隔离 Windows DSH 后，将两份冻结回执的不一致从 1 项重算为 0，原稿和实质证明原样。正式桌面仍为 0.7.35。

首次换入新核验契约后，原首审重核并通过。同一个独立复核会话从新版本的 `prepare` 得到了 11 个当期待核块，却在未提交任何一条本轮证明时主动挂起，理由引用了旧版本已经耗尽的重核。原生读包确认没有给它首审回执或理由。现行实现记录同一工件和目标升级时的契约版本，并在原审核会话的阶段提示和 `prepare` 明确告知该旧阻塞已失效、用本轮 `inventory` 独立核验。不得为解阻揭示另一道审核的理由。

## R80 的 13,185,233 Token 花在哪

按原生响应逐条去重，首审 6,150,379，独立复核 1,928,822，总控 4,375,792，执行方 730,240。两道审核共 8,079,201，占 61.27%。首次卡住的阶段共 3,867,579，原会话续做共 9,317,654。定向重核的时间窗内，两道审核直接消耗 1,413,498。

四组已明确的参数或旧稿结构错误共对应 37 次工具拒收。把发出错误调用的响应和下一条同角色响应去重，得到 49 次响应，共 2,840,281 Token，其中 2,787,072 为缓存读取。这部分包含同一响应里有效的工作，无法直接算成可节省用量。全程 12,746,368 是缓存读取，占提示输入的 97.58%。未命中输入和输出合计 438,865 Token。记录只按原生响应归因，不按 Token 推算账单，也没有启动额外的对比或优化实验。
