# 0.7.36 · 审核参数与用户澄清

上级为[实验与验收](README.md)。前一轮原生记录见 [R80](observations-0.7.35-delivery-outcomes.json)。

## 真实审核反复补参的根因

| 现象 | 原始调用与成功回执 | 处理 |
|---|---|---|
| 独立复核同一项目规则块反复报缺规则或前提 | 失败包已有规则和前提，但写在 `parts[]` 顶层；部分包只移动了 `rule`。真实 `prepare` 示例也把 `rule` 展示在顶层。规则、证据和判断移到同一个 `inference` 后获得回执 | `prepare` 提供嵌套示例，报告实际放错的字段。纯规则允许空前提，需要应用到记录时仍须交已核原始材料 |
| 首审和独立复核反复重交相同处置 | 成功与失败的处置值及定位不变。本角色对具体位置的覆盖证明改成新版类型后才过。原错误只报第一个事项和「正文或大白话」 | `coverage status` 和最终拒收列出本角色全部未满足的证明、事项、正文或大白话的实际行及覆盖块，已正确的处置回执可原样提交 |
| 独立复核第一次已有正文和大白话的位置，仍报位置不足 | 真实输入缺的是同级 `decision` 字段 | 分开报缺处置值与缺位置。准备包标清独立复核何时需要自己的 `outcomes` |

遗漏标点、使用未登记的原文行和未填 `sourceRelation` 仍按真实证据或实际入参处理。两道审核仍分别判断证据能支持的内容，最终审核和关单继续用角色各自的当前证据。

已批准的原生用例使用一条演练发布记录和一份带采集摘要的 GitHub 官方摘录。记录同时给出失败的自动检查和放行的人工复核；当前项目规则没有指定两者谁优先。等待状态必须来自原生宿主，不使用任何预置的用户回答。Windows 确定性覆盖分别演练两条业务决定，并维持当前实际原文校验。
