## 新需求的接单门槛

0.7.15 对照中，Building-loop 后三关把首关原字节送入待首审。这轮记录派单前基线，要求接单方读取当前需求，然后有真实实现结构变更，或有针对本轮新增测试的可信回执，才能送同一套首审。两条路径都不表示审核已通过。旧的执行中记录无派单前快照，不追溯套用该门槛。

Windows DSH 真实宿主的定向测试用确定性的本地调用脚本驱动。原实现已支持转小写与首尾去空格。独立 pytest 原套件 1/1，新套件 2/2，新用例 `trim-outer-spaces` 是当前要求。第一次原样提交缺回执被拒；第二次签名正确但绑定其他实现字节被拒；第三次回执绑定实际未改的实现及当前目标，进待首审。该测试不使用 DeepSeek，因此不产生真实模型用量数据。[原生回执与 pytest 观测](observations-0.7.16-code-intake.json)

同一运行包的本地测试 302/302，通过 Python、Markdown 内置解析器的可重建校验。还覆盖注释、排版或仅改测试不算实现、实现真改后完整读回、旧目标、错套件、错签名、恢复时保留原基线等。结构比较用于挡住没有实际实现变化的交付，无法证明任意改动满足需求；特别是新增测试是否准确覆盖需求，仍取决于独立运行者与实际测试。

0.7.17 只追加私有表格任务的开工交接隔离，代码接单模块字节不变。最终包 SHA-256 `6480f219246660800dd6f49538660ba640e2a5310eeaa83ca1698a1f203e7dcd`，本地 304/304，再次通过同一原生签名测试。[最终包原生观测](observations-0.7.17-code-intake.json)

必要注释按实际约束与行为给分，标准模式四关为 1/4、4/8、6/10、6/12；Building-loop 为 2/4、5/8、7/10、7/12。两边都出现被实际行为推翻的注释；第四关的旧包保护说明两边均为零。具体策略见[代码注释验收](../docs/code-comment-acceptance.md)：在真正作决定的函数或分支旁写原因和边界，再让独立运行者用最小案例验证。比如“全部未变时保留旧包”要核对清理后包还在、字节没变，不能凭注释自证。

职责边界、简洁、内聚和可用性各按 0–2 分，标准四关为 5、5、4、2/8，Building-loop 为 4、4、4、3/8。末关标准 1,110 行，部分修改在清理时删掉刚写出的包，入口还有语法错误；Building-loop 1,473 行，包含未使用的临时代码，第四关未实现增量包重写。第三关两边都识别等长但内容变化的文件；Building-loop 在该探针的事件摘要与写入字节相同，标准模式在受控修改源文件时出现分离。注释得分和行数均不能抵销可运行性问题；评分位置和实际探针输入输出保留在 `quality` 中。

性能样本仅给与参考事件摘要完全一致的输出计时，包含 WSL 沙箱和 Python 启动。伦敦时区下，Building-loop 首关 500/2,000 文件中位数为 59.4/64.2 ms，末关工作区的松散文件增量样本为 72.0/96.0 ms。末关样本走增量比较，不测试增量包重写；标准模式四种运行均未生成符合参考的事件，不能做两模式速度排名。没有测内存峰值。
