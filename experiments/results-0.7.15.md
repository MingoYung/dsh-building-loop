## SlopCodeBench 长任务

使用 [SlopCodeBench](https://github.com/SprocketLab/slop-code-bench) 公开题 `file_backup`，题库固定于 [9cd9ca3a](https://github.com/gabeorlanski/scb-problems/tree/9cd9ca3a51c3d3e2a99d2488a25baf73a2204451/file_backup)。四关依次加入调度模拟、策略和打包、目的地与增量、增量包重写。两种模式各把自己的上关代码带入新会话，收到同一份当关规范，评测侧独立保留测试和参考解。标准模式照常使用原生工具；Building-loop 使用当前工作区白名单和角色约束。为单独看代码实物，观察止于标准回合完成或上限、Building-loop 首稿提交或上限，不把进入 `review-ready` 算成功能通过。

评分器运行在隔离的 WSL Linux 环境。第一次直接使用 Windows 检出文件，CRLF 改变了测试资产的字节与 SHA；该无效分数留档。复跑逐个核对 271 个文件的 Git blob，恢复其中 218 个 CRLF 转换后的原始字节。参考解按关累计通过 32、50、68、89 项，随后使用同批夹具评价候选。每关 125 秒。该实验是用原题和原测试对比 DSH 两种原生模式，时间限制、权限和外部执行适配由本实验设置，不能视为官方榜单成绩。

| 检查点 | 标准模式：累计通过 | Building-loop：累计通过 | 标准模式／Building-loop 新增测试通过 |
|---|---:|---:|---:|
| 1：调度与排除 | 8/32 | 21/32 | 8/32 · 21/32 |
| 2：策略、校验与打包 | 9/50 | 23/50 | 1/18 · 2/18 |
| 3：目标目录与增量 | 7/68 | 23/68 | 3/18 · 0/18 |
| 4：增量包重写 | 8/89 | 23/89 | 1/21 · 0/21 |

标准模式四关有连续代码修改，第 1、4 关在上限截取源码。第 3 关后前两关的累计通过数从 9 降为 4。Building-loop 四关都到 `review-ready`，第二至第四关却保留了第一关同一个源码哈希。现有工作区的 `intake` 指南提示保留原稿，而实际源码从未增加备份策略和增量功能。短时间和低用量须与这种未交付一起解释：四关已返回用量标准模式 3,376,588 Token，Building-loop 606,493 Token；其中缓存读取分别是 3,223,424 和 485,888。

逐段检查必要注释、架构、简洁、内聚和可用性。首关有两项重要约束，标准模式注释 3/4，Building-loop 2/4。到第四关六项必要约束，分别是 7/12 和 2/12；后者未实现四项新约束。两份源码都写了与实际行为不符的 DST 说明。标准模式把事件抽到独立模块，后来名为 `schedule.py` 的文件仅重导出，排程、匹配、归档和存储仍集中在 `storage.py`，从三文件 736 行增长到四文件 1,439 行。隔离内存探针证实全未变时会请求删除所有旧包，注释中有关保留旧包的承诺未兑现。Building-loop 单文件 721 行的规模没有变化，同样没有覆盖新增行为；不能拿这一点当作简洁或低耦合的胜利。

只对事件输出与参考解一致的工作负载计时。首关伦敦时区、500 个文件时，五次端到端中位数标准模式 62.6 ms、Building-loop 57.2 ms；2,000 个文件时 71.6 ms 和 60.0 ms。时间含 Python 启动和沙箱开销。首关 UTC 的标准输出不符，末关增量样本两种模式都不符，故没有对应的速度排名，也没有内存峰值测量。 [四关观测、逐条测试失败、质量证据和时间样本](observations-0.7.15-long.json)
