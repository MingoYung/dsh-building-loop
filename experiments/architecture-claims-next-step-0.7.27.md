## 机制

1. **项目只登记关键职责。** 复用现有架构注册。由业主在授权范围内登记带 ID 的约束，每条绑定原条款文件、行号和内容摘要。机器无法从条款确定触发条件或是否禁止重复实现时，保留待确认项。协议形状、信任边界、错误优先级、跨模块职责等可登记为关键条款，纯解释性文字继续留在原架构稿。现有导入允许表保留为独立检查。
2. **一条约束只描述一个触发条件和结果。** 最小记录包含条款引用、入口或操作范围、触发条件、可见结果、判定归属和授权的证据类型。需要定序时引用另一条约束的 ID。比如“非对象”与“必需字段缺失”单列；“入口兜底”和“入口透传”也单列。架构稿可以引用 ID 并解释原因。宿主生成的表列出观察到的真实归属，解释文字不得覆盖宿主核验结果。
3. **把规范、计划和已实现事实保存在不同字段。** 业主条款代表意图，总控可在开工前登记拟由某模块实现，只有签名源码证据能形成当前事实。签名版本、条款或架构稿改变后，按变更的 ID 重新核验。总控在阶段内能看状态、条款、文件路径、行号、函数名和证据摘要。源码读取仍由获授权的执行方、首审和独立复核完成。
4. **自动从源码提取有限的证据。** Python 可以提取完整注册范围内的直接导入、可解析的本地调用、明确的条件、分支退出和字面错误码。同函数、同一顺序块中直接提前退出的分支可核验先后。只有能确定调用绑定和控制流时才把关系延伸至跨函数。可以记录同一错误码存在于不同分支，但绝不把任一个分支当作所有同名触发条件的归属证据。解析失败、别名不确定、跨语言或动态派发不强行下结论。
5. **运行结果与定位证据各有职责。** 用已授权的确定性测试输入验证输出，用签名源码位置或可信运行器的受限路径证据验证是谁作了判定。运行输入使用既有配方授权、超时、摘要绑定与签名。运行器验证在冻结副本上进行，业务模型拿不到隐藏用例。输出一致时，可能仍然由错误模块作了决定。
6. **发现冲突时定点补正。** 明确反证的结构化主张由宿主直接退回，回执带条款 ID、当前源码位置、复现方式和观察值。关键主张证据不足时保持待核验，补证或澄清后再处理，不能作为默认通过项。自由说明存在具体冲突时，独立复核能按当前源文件位置提交架构发现。首审和独立复核分别读取自己的授权材料，独立复核不能读首审结论。已有签名回归、事实溯源和三级文件检查继续沿用。

### 如何区分同一个错误码

| 条件 | 可见结果 | 对应证据 |
| --- | --- | --- |
| 已成功解码，顶层不是对象 | 返回 invalid-request | planner 的显式类型拒绝分支。输入列表或字符串可验证结果，分支位置确认判定归属 |
| planner 意外抛出异常 | 入口兜底也可能返回 invalid-request | release 的 except Exception。它说明故障路径，不能证明 release 验证了顶层类型 |
| 解码成功，顶层是对象，但某项字段不合格 | 由已登记的字段规则决定错误码 | 单独给出字段、运行输入和判定位置。原稿如果把缺键、多余键、非对象混写，就逐条求证 |
| 上层调用校验函数并输出其结果 | 上层对外返回原错误码 | 直接委托和透传证据。不会给上层增加业务判定职责 |

## 首批实现和验收

先做一个签名 Python 垂直切片。仅支持源码可以确认的顶层形态、已授权的局部静态导入、确定的拒绝分支。用现有登记路线供总控查看当前事实，给首审和独立复核增加按约束 ID 核对及补证。跨函数顺序、拒绝重复判定等需要显式条款和足够的代码或运行证据，再增加相应支持。

- 用两份集成包短题 G1 分别验证“混合多个条件和错误码”与“同码不同触发”。错误归属应退回，现有正例和 transport 兜底描述应通过。
- 用硬题两轮的 G3/G4 复核。合法的入口导入图保留，越界的两条边在启用业主约束时退回。对 wrong codec、动态批量分发、重复策略判定、身份键职责分别出状态和证据，不能把其中一项通过用于另外三项。
- 用公开条款与现场正例测试未规定的顺序。G2 的坏 action 和坏预算可作为对照运行，但不会凭实验结果变成业主规范。准确的 r-eXVclv G2 原稿复放通过。至少加一个跨函数和一个无法安全确定调用的通用负控制。
- 先用零模型宿主回归确认状态迁移和权限，再用真实 DSH 短任务与多模块盲测比较通过率、误退、补查次数、Token 和缓存命中。只有实测能说明新字段的维护成本是否值得。
