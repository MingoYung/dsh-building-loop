# 0.7.23 可执行代码审核和派单前交接

本轮继续 [0.7.22 的长工程对照](results-0.7.22.md)。当时合法 Python 被首审和终审先后判成语法错误，另一轮将符合要求的观察当作阻塞项。还有一次两个角色都批准了错误的架构示例，尽管源码功能已通过。

## 两种模式实际收到了什么

两种模式的中文用户消息逐字相同，都明确要求先写模块边界、实施顺序、回退依赖、验证方法，再改代码。在非显然的重放、图顺序和安全约束旁，说明代码为什么这样做。共享规格另外限定四模块职责、原有导入方向、外部接口和标准库。G2 由所有者更新生产范围、暂存配额和回退保留要求，要求新会话继承已验收行为和架构，实际实现、验证新目标。

0.7.23 给两种模式的共享规格和初始架构模板同时加上「可执行示例」章节，要求写成能独立运行的输入和预期输出。模型、四份初始代码、18/21 项签名评分、中文用户消息和 210/420 秒窗口沿用旧对照。Building-loop 接入签名、角色、账本和授权复现，标准模式继续使用 DSH 原生工具。每种模式的 G2 从自身 G1 产物开始。若 G1 未结束，则隔离已冻结的副本用于诊断，同目录接手不计通过。

每次候选由模型之外的 WSL bubblewrap 评估，固定用例在只读源码快照执行，输入和答案留在受信评估侧。四项导入边界、四项 I/O 边界、必要注释和架构正文另核。作者撰写的可执行示例按真实输出来评估，与固定评分分别记录。缓存命中按所有已返回的缓存读取除以全部输入计算，未返回用量的请求保留为未知。

## 机制和确定性回归

- 回执中可选观察与必修缺陷分别登记。有效条目保留，只改错项。必修缺陷需要具体的预期、实际差异及授权源码位置。运行和语法退回要引用本角色、本签名版本的受信复现，事实来源、全文覆盖、数字预检和签名路径保留。
- 总控在三级正文登记独立可执行示例。首审和独立复核分别运行当下的签名稿，断言差异定位到原示例。错误示例退回总控，真实代码缺陷按原机制退回执行方。总控修改预期后，两个角色重新核对新架构版本。本地完整角色链从错误示例、拒绝提前提交、只修架构、分别复跑走到复盘。已完成的同角色示例重试直接取当前版本的记录。
- 派单前目标变更允许同目录接手，宿主校验实际前任身份、目标变化和旧单元或账本是否已派发。隔离原生 Windows DSH 在最终包验证了写入 G1 架构、确认 G2、拒绝误派 K01、K02 进入执行及拒绝旧会话强制写入。G1 原架构字节和正式 Profile 保持一致。该探针以确定性模型替身验证宿主。 [最终原生接手](observations-0.7.23-planning-handoff-batch.json) · [较早候选记录](observations-0.7.23-planning-handoff-b4ab4882.json) · [批量修复前的同一探针](observations-0.7.23-planning-handoff-final.json)

## 放行状态

必跑示例的隔离配额、批量执行、合法语法的反证以及派单前原地接手均有通过证据。真正已知的剩余问题是，宿主已经复现的差异仍要求审核模型重填一套归责字段，容易反复填错。账本登记为待修。宿主可以直接保存输入和输出的差异，审核只需定位原始需求、源码并裁定修改代码还是架构。若判断不了，保留未解决状态。单凭示例期望被改成当前输出，无法证明符合用户要求。自由架构文字中的错误推断也仍可漏过，模块边界若由项目明确登记，可以直接检查真实导入。最终候选未通过完整验收，正式 DSH 保持 0.7.18。ClearAI 三方对照待最终完整验收和桌面同步之后。
