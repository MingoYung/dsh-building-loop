# 0.7.13 由会话判断并开工

验收在 Windows 已安装的 DSH NEXT 的隔离 Profile 进行。实测使用相同的运行时、原生聊天界面和模型路由，使用合成任务及合成工作区。回环用例检查真实请求与磁盘；真实用例通过 DeepSeek Flash 检查会话语义和执行行为。

## 实测中发现的问题

| 观察 | 处理 |
|---|---|
| 新建的执行子会话在 Windows 继承了父会话的原生工作目录，原型因检查这个目录而阻塞。 | 文件权限由宿主绑定的会话项目根和当前工作单元中的确切子会话身份确定。测试向父目录放入独立标记，核对实际子会话请求和工具。 |
| DeepSeek 在开工后的第一次请求拒绝全部 `defer_loading` 的工具。 | 按真实步骤准入的工具和原生请求历史对照，仅在缺少立即可用的工具基线时启用 DSH 的原生新请求系列。同一会话继续，角色、白名单和其他项目的配置沿用原值。 |
| 首次重试使用注册表中的工具，已退场的提议工具仍出现在注册表内，导致没有建立新基线。 | 改为使用 DSH 的步骤准入结果。回环测试也拒绝全延迟声明，以复现真实供应商的报错。 |

提示词总量为非缓存输入与缓存读取之和。失败请求没有供应商用量，保留为未知。测试输入包含普通问答、目标不成熟、引用式开工、多轮讨论后提出计划、在界面确认、直接开工及子会话起稿。缓存比例属于当次请求集合，包含测试顺序及复跑影响。

各轮检查点、按会话的用量、失败分类与交付摘要见[公开实验数据](observations-0.7.13.json)。

按真实准入重建后的首次运行，测试脚本误将原生工具参数 JSON 字符串当作对象，读回断言因此失败。复核原生压缩会话记录，已见执行子会话写入 `DELIVERY.md`、按相同摘要读回并成功提交 `review-ready`。这一次的断言失败和真实阶段均保留。

## Windows 宿主验收

候选运行包 SHA-256 为 `4843e1c0c67b9f58e1b46027d7e3b3823d00298c247fd2dc9ed5b8860a13d6fc`。282 项 Node 回归通过。普通预设标识与正式沿用的 `paidan` 标识分别通过 15 项及 14 项原生界面检查。两组回环均有 35 次模型请求，全延迟声明为 0。用例覆盖当前会话材料、重放和过期确认、工作区文件越界、同目录的独立任务、旧授权复用、原生子会话写读及首审入口。

最终真实 DeepSeek 验收 11 项通过。普通问答、目标尚不明确和引用中的开工语句留在聊天。成熟提议带入前面两轮的观察，确认后写出 8,595 字节初稿并进入首审。另一条会话用明确指令直接启动，执行子会话写出 224 字节清单，按同一摘要完整读回并通过接单，首审生成回执后到达 `first-audit-ready`。独立反证与最终结单超出本轮观测窗口。

正式桌面使用同一候选包的 20 个运行时文件升级，保持 `paidan` 原生会话标识。通过原修复启动快捷方式重启，旧草稿继续显示 `building-loop`，输入框恢复为普通入口。正式 Profile 的包清单和锁文件摘要一致，原工作区未生成授权文件。正式点验限宿主启动和界面加载，完整确认与真实模型测试在隔离 Profile 执行。

复查发现，前次放入的运行目录没有登记为 pnpm 依赖，后续刷新插件依赖时被移除。重启后独立反证及结单已补测，正式部署改用内置插件管理器。 [复查与修复](results-0.7.14.md)
