# 项目索引契约 v1

> **定位**：本件＝**「一个项目怎么被接手」的机制正本**。只管三件事：**分层**、**每层允许怎么改**、**索引长什么样**。
> **零硬编码**：一切可变项写成 `<占位符>`。**禁**出现任何具体项目名、路径、角色名、编号体系——那些由**项目自己的**索引文件与项目根 `AGENTS.md` 提供。
> **单一正本**：格式只在本件写全；项目侧只写「它的索引文件放在哪」。
> **配套脚本**：同目录 `check.ps1`——按索引重算哈希、打印「变了什么」、可 `-Rebuild` 回写。

---

## §一 三级分层

**判据不是「文件多大」，是「读者是谁、什么时候读」。**

| 级 | 名字 | 放什么 | 读者 | 体量 |
|---|---|---|---|---|
| **1 级** | 全貌级 | 这个项目是什么、分成哪几块、每块的 2 级件在哪、当前状态一句话 | **每一个新会话，第一个读** | 一份，几百行以内 |
| **2 级** | 分块级 | 这一块是什么、它有哪些 3 级件、块内约定、块内当前状态 | 动这一块的人 | 每块一份 |
| **3 级** | 正文级 | 真正的规格、代码、记录、产物 | 干活的人，按 2 级指路去读 | 不限 |

**两条硬规矩**：

1. **每一级只指向下一级，不越级复制内容。** 1 级不抄 2 级的正文，2 级不抄 3 级的正文——**只给路径与一句话**。
2. **级数固定三级，禁再加级。** 想细分就在 2 级件里分节，不要造 4 级。

**为什么不按大小分**：按大小分会得到一堆「因为文件小所以是 1 级」的垃圾。按读者分，1 级永远是「谁进来都该先看的那一份」。

## §二 三条写入规则（本契约的内核）

**每一份被索引的文件先归到下面三类之一，规则随类别走。**

| 类别 | 放什么 | 规则 | 允许谁写 |
|---|---|---|---|
| **正典** | 架构、决策、约定、对外接口、路线图 | **逐字保留，整份替换**。**模型永远不许改写、摘要、润色它** | 人；或人明确指派后由 agent 起草、**人批准** |
| **状态** | 当前进度、交接、日志 | **覆盖**——新的取代旧的，**绝不累积** | 执行方写完即覆盖；**读完不写** |
| **知识** | 概念、实体、经验、案例 | **就地加深**——新内容更新已有条目，**不是并排再堆一份** | 任何人，但**必须改原地，不许加副本** |

**为什么这三条必须分开——这是全套设计里最值钱的一句话**：

> **并集合并表达不了「不再成立」。**

周二解决的阻塞，如果周三用「累积」写进去，它会复活。反过来，一份架构决策如果被模型「润色」过，它就失去法律效力，之后没人敢拿它当依据。**状态要覆盖，正典要逐字，知识才累积。**

**判不准时怎么办**：按**更强的那个**走——**宁可逐字，不要摘要**；**宁可覆盖，不要累积**。失败方向要指向「丢信息」，不能指向「造假信息」。

## §三 索引格式

索引＝**一份 JSON**，只登记「值得被索引的文件」，**不登记全树**。

```json
{
  "spec": "project-index/1",
  "project": "<项目名>",
  "root": "<项目根：绝对路径，或相对本索引文件的路径>",
  "generatedAt": "<iso-8601>",
  "entries": [
    {
      "path": "<相对 root 的路径>",
      "tier": 1,
      "rule": "verbatim",
      "route": "read-first",
      "sha256": "<64 位小写 hex>",
      "bytes": 12345,
      "updatedAt": "<iso-8601>"
    }
  ]
}
```

| 字段 | 取值 | 含义 |
|---|---|---|
| `spec` | 固定 `project-index/1` | 版本。读者不认识的版本**拒绝**，不猜、不改 |
| `project` / `root` | 字符串 | 这份索引描述谁、根在哪 |
| `generatedAt` | iso-8601 | **最后一次重建索引**的时间——不是任何文件的时间 |
| `entries[].path` | 相对 `root` | 被索引的文件 |
| `entries[].tier` | `1` / `2` / `3` | §一 的层级 |
| `entries[].rule` | `verbatim` / `supersede` / `accumulate` | §二 的类别 |
| `entries[].route` | `read-first` / `on-request` / `not-at-start` | 进场时给不给正文（§四） |
| `entries[].sha256` | 64 位小写 hex | **这份文件当前内容的指纹——索引的全部价值在这** |
| `entries[].bytes` / `updatedAt` | 整数 / iso-8601 | 给人看的，**不参与判定** |

**四条硬规矩**：

1. **索引是派生缓存，不是真源。** 真源永远是文件本身；索引随时可由 `check.ps1 -Rebuild` 重建。
2. **只登记少量文件。** 判据＝「新会话该不该知道它」。**判不准就不登记。**（一个 90 G 的项目里，真正值得索引的通常是**几十个**文件。）
3. **`read-first` 要吝啬。** 它意味着「每个会话都要读它的正文」。**超过 5 份就该重新想。**
4. **一个文件只能出现一次。** 重复登记按错误处理。

**为什么这套能压住「同步不及时产生的错误」**：登记的文件少 ⇒ 进场时**重算全部 sha256 的成本可以忽略** ⇒ 每次进场都真的知道「哪几份变了」。**不是靠人记得更新索引，是靠每次进场都重算。** 索引里的 `sha256` 是**对账基准**，不是**信任来源**——它与真文件不一致时，**一律以文件为准**，并把索引标为过期。

## §四 进场包（bootstrap）

**新会话进场＝一次组装，四件，按此序**：

1. **1 级全貌件**——永远第一份，且**给正文**。
2. **上一份交接**（`rule: supersede` 的那一份）——**只给最新一份**，旧的忽略。
3. **变更清单**——`check.ps1` 的输出：哪些登记文件的哈希与索引不符、哪些缺失。
4. **`read-first` 的正文** ＋ 其余登记文件的**路径清单**（只给清单，按需再开）。

**选择规则**：

| `route` | 进场时 |
|---|---|
| `read-first` | **给正文**——无论变没变（理由见下） |
| `on-request` | 只出现在清单里，**按名打开** |
| `not-at-start` | **连清单都不出现**（它仍在索引里，按名仍可取） |

**`read-first` 为什么不看「变没变」**：变更清单是给「读一次就记住」的文件省钱的；而 `read-first` 是「不读这个别开工」，那是**每个会话**的指令——一个续做的会话手里有哈希、手里没正文，按「只看变更」的规则它拿到的会是一个空包。

**读从不写**：进场**不修改任何文件**。它只产出「这次给出了哪些文件、哪个哈希」；**由进场方在它自己第一次写入时记下**，记在状态类文件的固定一节里。

## §五 只收窄

**任何被派生的东西——子系统、模块、工作单元——继承父的范围与权限时，只能收窄，不能放宽。**

- 派生物允许的范围 ⊆ 派它出来的那个范围。
- **收窄自动生效；放宽不自动生效**，必须显式批准。
- 没有批准时，有效范围**只可能缩小**。

**为什么**：不这样，一句「顺手改一下」就能把边界吃掉，而事后没人看得出来。这条的好处是**可判定**——「新范围是不是旧范围的子集」不需要判断力，一个脚本就能判。

## §六 与作业协议的接口

本契约只管「知识怎么摆」；**怎么派活、怎么交付、怎么验收**在 `dispatch-protocol` 那一份。两者只有两个接点：

1. **工作单元开工前**：执行方先读 1 级件与进场包（§四），**再**动手。
2. **工作单元交付时**：凡改动落在被索引文件上的，回执里必须附**新的 sha256**；由派单方核对后更新索引。

**索引不参与验收判定。** 它是地图，不是法官。
