# 必要代码注释的交付验收

这份约定用于现有的派单与验收。代码任务要求解释关键约束时，派单可直接用这句话。

> 对新增或改变的代码，只在非显然的不变量、例外或数据保护分支旁写注释，说明为何这么做、何时成立。用实际控制流和可观察结果核对注释。显而易见的代码不用注释。

先对照本轮需求和差异，找出改错后可能悄悄改变结果、覆盖旧数据或使失败看起来像成功的地方。把解释放在实际做决定的函数或分支旁。一条注释应说明可复核的理由或边界，例如哪段顺序不能换、哪些字节参与摘要、退出时哪些文件仍要保留。如果已有说明能准确覆盖改动，可继续沿用。改动使说明过时，就在同一份改动里更新它。

| 改动涉及 | 就地解释 | 对应核对 |
| --- | --- | --- |
| 排程时区与窗口 | 若将本地触发时刻转为 UTC 比较，解释转换与分钟取整的边界。只有实现确实做了本地时间往返校验，才能承诺跳过 DST 缺口。 | 窗口右端刚好到期、窗口为零、春季不存在的时刻和秋季重复时刻。对照实现声明的重复策略。 |
| 文件筛选 | 解释 glob 针对哪一个来源根的相对路径，以及为什么首个匹配规则用于排除事件。 | 两条规则均匹配同一文件时，核对事件引用的规则与列表顺序。 |
| SHA-256 增量比较 | 说明摘要覆盖的是本次参与比较或实际写入的内容字节。旧摘要来自哪个已确认的目标版本，也要在读取边界说清。 | 内容变化但长度相同应重写。未变化应跳过，观察目标内容仍在。 |
| 确定性归档与分包 | 解释归档头字段归一化为何稳定摘要，明确包大小计算的是成员内容还是归档实际字节。若规则允许一个超限文件单独入包，在分包分支注明。 | 固定成员与顺序后重复生成 tar，比较实际归档摘要。再查正好到上限与超限单文件。 |
| 保留旧包 | 在重写或清理决策旁说明保留集合如何产生。包含未重写但仍有效的包，且仅当整个包匹配时才宣称原包不变。 | 全部未变时核对原包仍在、字节未变、事件如实报告。部分修改时核对旧成员完整、大小边界和清理范围。 |

例如，真正采用本地时间往返过滤 DST 缺口的实现，可以写 `# Round-trip through UTC to reject local times that never occur.`。将旧包保留集合用于清理的实现，可以写 `# Keep valid old packs even when no member was rewritten.`，并由全未变的用例证明旧包仍存在。这两句都应贴着相应决定。只写“转成 UTC”或“清理旧包”没有补充理由。源码还没落实某项保证时，应先修实现或把注释收窄到已经成立的行为。

验收从差异出发。对每一项实际适用的约束，定位代码行和已有说明，再用相关测试或最小可观察用例核对。回执记录仍缺解释的具体位置、与行为不符的说明和核对结果。建议用“文件与行号、约束、观察结果”描述一项证据。对照评审可把每项记为缺失或错误、准确但不完整、准确且解释了原因或边界。注释条数仅作描述，代码职责、功能正确率和运行性能各用自身证据判断。

签名代码任务在派发时收到必要注释要求。纯实现代码的首审与独立复核都要核对变更文件的必要注释、当前源码和实测约束。宿主能从签名源码证实的矛盾直接返回给执行方。例如 Python 内置列表用 `bisect.insort` 时，二分找位置的复杂度不能写成插入整体的复杂度。宿主给出说明行和操作行，修正后按新字节重跑签名；有限用例跑得快不能证明复杂度。其他说明是否准确、必要注释是否缺失，仍由两次独立核验结合当前源码判断，未达标时给出具体位置及理由。 [代码送审与核验](../governance/code-regression.md#已验证稿的送审与代码核验)
